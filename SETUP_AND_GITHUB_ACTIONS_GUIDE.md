# Setup and GitHub Actions Guide

## Before you start: provision the infrastructure (manual, one-time)

GitHub Actions automates the **code pipeline** — testing, building images, deploying to
the cluster — but it cannot create the cluster itself. The underlying Azure infrastructure
(resource group, ACR, AKS, Postgres) must be provisioned first, by hand, using
Terraform. This is a deliberate choice: infrastructure changes are rare, high-risk, and
deserve human review; code deploys are frequent and benefit from full automation.

Run these once from your terminal before anything else:

**Step 1 — Log in to Azure**

```bash
az login
```

This opens a browser window for you to pick your Azure account. After you sign in,
the Azure CLI stores a **short-lived access token** in `~/.azure/` on your local
machine. Every subsequent `az` command (and Terraform's `azurerm` provider) reads
that token automatically — no username or password is ever written to your project
files.

| Credential | Where it lives | Committed to git? |
|---|---|---|
| Azure login token | `~/.azure/` (your home dir) | No — managed by the CLI |
| Terraform state | `terraform/terraform.tfstate` | No — gitignored |
| Real API keys | `k8s/aks/chart/values-secrets.yaml` | No — gitignored |

**Step 2 — Provision the infrastructure**

```bash
cd terraform/
terraform init       # downloads the azurerm provider
terraform apply      # creates resource group, ACR, and AKS; takes ~10 minutes
```

Terraform writes the resulting resource IDs to `terraform/terraform.tfstate` locally.
This file is gitignored — it can contain sensitive data and is regenerated by Terraform
anyway. If you want multiple people to share state, uncomment the `backend "azurerm"`
block in `terraform/main.tf` to store it in an Azure Storage Account instead.

Once `terraform apply` finishes you have a running cluster and a container registry.
Everything after this point — building images and deploying the Helm chart — is handled
automatically by GitHub Actions whenever you push to `main`.

> **Can GitHub Actions provision infra too?** Technically yes — you could add a Terraform
> step inside a workflow. In practice it is almost always kept manual (or behind a strict
> manual-approval gate) because destroying or recreating infrastructure is irreversible
> and usually not something you want triggered by an accidental push.

---

This repo has two workflows in `.github/workflows/`:

- **pr_checks.yaml** — runs lint + tests on every pull request to `main`.
- **deploy.yml** — builds the images and deploys to AKS every time you **push to `main`**.

This guide gets `deploy.yml` working: get credentials from Azure → store them as
secrets → push to main to deploy.

## 1. Create a GitHub Repository

If you haven't already:

1. Go to [github.com](https://github.com) → **New repository**
2. Name it `aks-chatbot-aiops`, set it Public or Private
3. Do **not** initialize with a README (you already have one)

Then connect your local repo and push:

```bash
git remote add origin https://github.com/alibaygi/aks-chatbot-aiops.git
git push -u origin main
```

> Pushing to `main` triggers the deploy workflow. Finish the Azure setup (Sections 2–3)
> and store the GitHub Secrets (Section 3) **before** your first push, otherwise the
> Azure login step will fail.

## 2. Get Credentials from Azure

The workflow logs in to Azure with **OIDC** (no password is ever stored). You run
these commands **once** from your terminal. They assume your ACR + AKS already exist
(Phase 1 of the README). Run the chunks **in order** — each one reuses variables set
by the previous chunk, so keep the same terminal session open.

**Chunk 1 — log in and set variables** (edit the 5 project values to match your resources)

```bash
az login
```

```bash
SUBSCRIPTION_ID=$(az account show --query id -o tsv)
TENANT_ID=$(az account show --query tenantId -o tsv)

RESOURCE_GROUP="rg-gen-project"
AKS_CLUSTER="aksclusterdev"
ACR_NAME="akscontainerregistrydev"
GH_ORG="alibaygi"
GH_REPO="aks-chatbot-aiops"
```

**Chunk 2 — create the app registration**

```bash
APP_ID=$(az ad app create --display-name "github-actions-chatbot" --query appId -o tsv)
OBJECT_ID=$(az ad app show --id "$APP_ID" --query id -o tsv)
az ad sp create --id "$APP_ID"
```

**Chunk 3 — trust GitHub Actions from the main branch** (OIDC federated credential)

The deploy pipeline fires on a **push to `main`**, so you only need one federated
credential covering the `main` branch. Both the deploy workflow and PR checks use it.

```bash
# Trust the main branch (used by both deploy and PR checks)
az ad app federated-credential create \
  --id "$OBJECT_ID" \
  --parameters "{\"name\": \"github-main\", \"issuer\": \"https://token.actions.githubusercontent.com\", \"subject\": \"repo:${GH_ORG}/${GH_REPO}:ref:refs/heads/main\", \"audiences\": [\"api://AzureADTokenExchange\"]}"
```

> **Why not use release tags?** Azure AD federated credentials perform **exact string
> matching** on the subject claim — wildcards are not supported, despite being accepted
> during credential creation. A credential with subject `refs/tags/*` is stored but
> never matches any real tag (e.g. `refs/tags/v0.2.1`), causing `AADSTS700213` at
> runtime. The push-to-main trigger avoids this entirely: the subject is always the
> literal string `repo:ORG/REPO:ref:refs/heads/main`, which matches exactly.

**Chunk 4 — assign roles so the workflow can push images and deploy**

```bash
SP_OBJECT_ID=$(az ad sp show --id "$APP_ID" --query id -o tsv)
ACR_ID=$(az acr show --name "$ACR_NAME" --resource-group "$RESOURCE_GROUP" --query id -o tsv)
AKS_ID=$(az aks show --name "$AKS_CLUSTER" --resource-group "$RESOURCE_GROUP" --query id -o tsv)

az role assignment create --assignee-object-id "$SP_OBJECT_ID" --assignee-principal-type ServicePrincipal --role AcrPush --scope "$ACR_ID"
az role assignment create --assignee-object-id "$SP_OBJECT_ID" --assignee-principal-type ServicePrincipal --role Contributor --scope "$ACR_ID"
az role assignment create --assignee-object-id "$SP_OBJECT_ID" --assignee-principal-type ServicePrincipal --role "Azure Kubernetes Service Cluster User Role" --scope "$AKS_ID"
```

**Chunk 5 — print the three GitHub Secrets**

```bash
echo "AZURE_CLIENT_ID:        $APP_ID"
echo "AZURE_TENANT_ID:        $TENANT_ID"
echo "AZURE_SUBSCRIPTION_ID:  $SUBSCRIPTION_ID"
```

Keep that last output — you need it in the next step.

## 3. Store Secrets in GitHub

Go to your repo → **Settings → Secrets and variables → Actions → Secrets tab** →
**New repository secret**, and add these:

| Secret name | Value |
|---|---|
| `AZURE_CLIENT_ID` | `$APP_ID` printed above |
| `AZURE_TENANT_ID` | `$TENANT_ID` printed above |
| `AZURE_SUBSCRIPTION_ID` | `$SUBSCRIPTION_ID` printed above |
| `HELM_VALUES_SECRETS` | Full contents of your `values-secrets.yaml` (DB password + API keys) |

For `HELM_VALUES_SECRETS`, copy `k8s/aks/chart/values-secrets.yaml.example`, fill in
real values, and paste the **entire file** as the secret value:

```yaml
secrets:
  postgres:
    password: "your-strong-password"
  backend:
    secretKey: "output-of-openssl-rand-hex-32"
    openaiApiKey: "sk-..."
    tavilyApiKey: "tvly-..."
    langsmithApiKey: ""   # optional — only needed for LangSmith runtime tracing
```

> Secrets are encrypted and never shown again after saving. The workflow reads them
> as `${{ secrets.AZURE_CLIENT_ID }}` etc. — GitHub injects the values at runtime.

### Optional — turn on the evaluation gate

This is the LLM-as-judge quality check, and it's **off by default**. To enable it, go to
your repo → **Settings → Secrets and variables → Actions**, then add three things:

1. **Variables tab** → **New repository variable**
   - Name `RUN_EVAL_GATE`, value `true`
2. **Secrets tab** → **New repository secret** (add both)
   - `LANGSMITH_API_KEY` — from [smith.langchain.com](https://smith.langchain.com) → Settings → API Keys
   - `OPENAI_API_KEY` — from [platform.openai.com](https://platform.openai.com) → API keys (the judge model uses it)

> These are **GitHub-level** settings and are separate from the `langsmithApiKey` /
> `openaiApiKey` inside `HELM_VALUES_SECRETS`. Those run the live app; these run the
> evaluation gate in CI. It's normal to use the same key values in both places.

## 4. Trigger the Workflow (Push to main)

The pipeline is **push-based**: it fires automatically every time you merge or push
to `main`. To deploy a new version:

```bash
git push origin main
```

That's it. GitHub Actions picks it up, builds the images, and deploys to AKS. The
image tag is derived from the commit SHA + run number, e.g. `abc1234-42`, so every
build is uniquely traceable back to an exact commit.

You can also trigger the workflow manually without a push:

1. Go to your repo → **Actions** tab
2. Click **Build and Deploy to AKS** in the left sidebar
3. Click **Run workflow** → **Run workflow**

---

## 5. Watch the Workflow Run

1. Go to your repo → **Actions** tab
2. Click the running **Build and Deploy to AKS** workflow to open the logs
3. The steps run in order:
   - **derive image tag** → from the commit SHA + run number, e.g. `abc1234-42`
   - **(optional) eval gate** → only if `RUN_EVAL_GATE = true`
   - **Azure login (OIDC)** → fails here if a secret is wrong
   - **az acr build** → builds backend + frontend images inside Azure
   - **az aks get-credentials → helm upgrade** → deploys to the cluster

---

## 6. Verify the Deploy

After the workflow succeeds, check the cluster:

```bash
az aks get-credentials --resource-group rg-gen-project --name aksclusterdev
kubectl get pods            # frontend, backend, postgres should be Running
kubectl get svc frontend    # grab the LoadBalancer EXTERNAL-IP and open it
```

You should also see the new image tags in your registry:

```bash
az acr repository show-tags --name akscontainerregistrydev --repository chatbot/backend
```

## 7. Open the Chatbot in Your Browser

After the Helm deploy succeeds, the frontend pod gets a public IP via a LoadBalancer.
Run this once to find it:

```bash
az aks get-credentials --resource-group rg-gen-project --name aksclusterdev --overwrite-existing

kubectl get svc frontend -n default
```

Look for the **EXTERNAL-IP** column in the output:

```
NAME       TYPE           CLUSTER-IP    EXTERNAL-IP      PORT(S)        AGE
frontend   LoadBalancer   10.0.12.34    20.82.111.222    80:31234/TCP   2m
```

Open `http://20.82.111.222` in your browser — that's your chatbot.

> The IP may show `<pending>` for 1–2 minutes while Azure provisions the load balancer.
> Just re-run the command until an IP appears.

**Check all pods are healthy first:**

```bash
kubectl get pods
```

All three should show `Running` and `READY 1/1` (or `2/2` for the backend):

```
NAME                        READY   STATUS    RESTARTS
backend-7d9f6b-xkp2n        1/1     Running   0
frontend-6c8d4f-tn3qw       1/1     Running   0
postgres-0                  1/1     Running   0
```

If a pod is `CrashLoopBackOff` or `Error`, inspect it:

```bash
kubectl logs <pod-name>          # see what went wrong
kubectl describe pod <pod-name>  # see events (e.g. image pull failure, bad secret)
```

## Quick Reference

```
git push origin main
        ↓
GitHub Actions: deploy.yml
        ↓
derive image tag (SHA-42) → (eval gate?) → Azure login (OIDC)
        ↓
az acr build backend + frontend   (builds in Azure)
        ↓
helm upgrade --install            (rolling deploy to AKS)
```

| Need | Where |
|---|---|
| Azure setup commands | Section 2 (or README → Phase 2) |
| The 4 required secrets | Section 3 table |
| Trigger a deploy | `git push origin main` (Section 4) |
| Manual trigger (no push) | Actions tab → Build and Deploy → Run workflow |
| Watch / debug a run | Actions tab → click the run → expand the failed step |
| Open the chatbot | `kubectl get svc frontend` → EXTERNAL-IP → open in browser (Section 7) |
